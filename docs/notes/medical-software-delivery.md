# 把医学影像软件刻成光盘交付

> 2026 年 8 月。比赛要求把软件刻录到光盘上交。在这之前，我写的所有东西都只在"我这台电脑上跑得起来"。

::: info 先说结论
- "自动适配"听起来优雅，但交付时**可预测比优雅重要**：硬件降级不是一个配置开关，而是两套各自测过的发行配置；
- 界面不能靠看，要靠点：13 个页面、审计 265 个可点击元素、实际执行 192 次点击、零失败。这个数字比"检查过了"有说服力；
- 最后一公里踩的坑基本都不在代码里，而在路径、缓存和"本机早就装过"的依赖上。
:::

## 一、交付和演示是两件事

本地开发时我的判断标准很简单：跑起来不报错，界面看着对。刻盘交付意味着三件额外的事：

- 运行环境不由我控制：对方的显卡可能不支持 GPU 加速，甚至可能没有独立显卡；
- 装不了东西：不能指望评审现场有人执行安装命令；
- 没人替你解释："这里点一下再点那里"这句话传不到评审现场。

## 二、硬件降级不是配置项，是第二套构建

最初的想法是加一个开关：检测不到 GPU 就走 CPU。真做的时候才发现没那么简单——预处理尺寸、模型精度、批处理方式在两条路径上都不一样，某些依赖在纯 CPU 环境里根本装不上。更麻烦的是"自动降级"这条路没人测过：真降级的时候才第一次执行，出错也第一次暴露。

最后的做法是维护两套发行配置，各自跑通再打包。**交付物要的是可预测，而自动适配带来的恰恰是不确定性。**

## 三、界面要靠点，不能靠看

软件有十几个页面、两百多个可点击元素。人工点一遍要半天，点漏了自己也不知道。

所以用自动化测试驱动真实桌面应用遍历界面，逐一审计并记录结果：**13 个页面 / 265 个可点击元素 / 192 次实际点击 / 零失败**。这组数字后来直接写进了交付说明。

有个细节值得记：**能点击 ≠ 点了有用**。自动化能覆盖"按钮点下去不报错、界面不崩"，但"这个按钮的业务逻辑对不对"还是得人判断。所以分工是脚本负责覆盖面，人负责抽查关键流程。

## 四、打包时最容易忽略的是路径和缓存

最后一公里踩的坑基本都不在算法里：

- 开发机的绝对路径写死在某个配置里，换台机器立刻找不到文件；
- 编译缓存和旧构建产物混进发行包，包体莫名变大；
- 依赖在本机能装上，只是因为本机早就装过了，干净环境里装不上。

解决办法很土但有效：**在一台干净的机器上，从零走一遍解压、安装、启动的完整流程**，把它当成交付前的固定动作。

::: tip 性价比最高的一步
刻盘前在干净机器上走一遍完整流程，并且全程不要顺手装任何东西。这一步能同时抓出硬编码路径、缺失依赖和过期产物三类问题——它们都不会在自己的开发机上出现。
:::

## 五、光盘这个约束反而帮了忙

不能联网、不能改环境、必须离线自包含，这几条限制把很多"以后再说"的模糊地带直接消掉了：依赖要么打包进去，要么就不依赖。相比之下，可以随时打补丁的在线交付反而容易把问题留到最后。

::: warning 容易踩的坑
不要用"我这台机器上试过没问题"作为交付依据。开发机是全世界最不利于发现问题的地方——依赖齐全、字体齐全、路径正确、缓存都在。
:::

## 六、一点体会

写算法时我关心分数能不能再高一点；做交付时我关心别人能不能把它用起来。这两件事需要完全不同的思维方式，而后者在课程里几乎不会被训练。

刻盘这件事让我第一次意识到：**"做出来了"和"交付出去了"之间，隔着的全是细节。**

## 七、可复用的清单

- 硬件降级用两套各自验证过的发行配置，不依赖运行时自动适配；
- 交付数字要具体到可核查：页面数、元素数、点击数、失败数；
- 自动化负责覆盖面，关键业务流程留给人抽查；
- 发行包里不允许出现开发机绝对路径；
- 打包前清缓存、清旧产物，包体大小异常先查这两项；
- 在干净机器上从零走一遍解压、安装、启动；
- 离线交付比在线交付更容易做对，因为约束不允许含糊。
