# 长任务的工程化：进度、预算与中断恢复

> 跑几小时到十几小时的任务，和跑几十秒的任务是两类问题。长任务失败的方式几乎都不是"模型不够聪明"，而是跑到一半断了、额度用完了，或者第二天发现方向从一开始就错了。

::: info 先说结论
- 续跑的关键不是断点，而是**幂等**：把"处理到第几个"这种状态消掉，比维护它便宜；
- 进度必须在磁盘上，会话里说的"已经处理了 1.2 万条"在会话结束的瞬间失效；
- 并发上限从**服务端限额**倒推，不是从"我想多快"决定——拉满并发是负优化；
- 中断是正常路径：状态在外、操作幂等、结果可验证，长任务就变成"分几次做完"。
:::

## 一、一次 11.2 小时任务的真实时间线

2026 年 8 月的语料流水线，30,031 篇论文，单机加云端混合推理。任务前后跨了 11.2 小时，中间断网一次，没有人工干预就续上了。

| 时间 | 发生了什么 | 观察到的数字 |
| --- | --- | --- |
| 00:00 | 全量入队，开始处理 | pending 30,031 |
| 约 03:00 | 速率稳定，按完成量折算 | 约 1.3 秒/篇 |
| 约 05:00 | 网络中断，进程退出 | 一批任务停在 running |
| 中断后 | 直接重启，不去判断"从哪继续" | 重复执行不产生新记录 |
| 11:12 | 收尾 | 完成 30,018 篇（99.96%），失败按原因分类 |

真正值得记的不是 11.2 小时这个数字，而是中断后**没有人需要回答"现在跑到哪了"**——这个问题由任务表和幂等键回答。

## 二、进度落盘：任务表是唯一事实来源

长任务必须有一份外部状态，写到哪一步、哪些完成、哪些失败、失败原因是什么，都在里面：

```sql
CREATE TABLE tasks (
  hash       TEXT PRIMARY KEY,   -- 内容哈希，同时是幂等键
  path       TEXT NOT NULL,
  status     TEXT NOT NULL,      -- pending | running | done | failed
  reason     TEXT,               -- 失败原因分类，不写自由文本
  attempts   INTEGER DEFAULT 0,
  updated_at TEXT
);
```

好处不只是能续跑，还包括**可以从外部观察进度**，不必去翻会话记录：

```bash
python -c "from db import stats; print(stats())"
# {'pending': 13, 'running': 0, 'done': 30018, 'failed': 12}
```

## 三、幂等比断点续传便宜

续跑的实现比想象中简单，前提是幂等。每个文件先算内容哈希，处理过就跳过：

```python
h = content_hash(pdf_path)
if table.seen(h):
    return                      # 重复执行天然安全
table.enqueue(h, pdf_path)
```

这样就不需要维护"我处理到第几个了"这种脆弱状态：进程被杀掉、断网、重启，重新启动即可，恢复过程不需要判断。第一版按"断点"设计过，问题在于断点本身要跟多个处理阶段对齐，任何一处偏移都会漏掉或重跑一批。

## 四、预算与限流要提前算

长任务最容易在两种地方翻车：

- **接口限流**：并发拉满导致整体排队，比低并发还慢；
- **额度耗尽**：按小时或按量计费，跑到关键阶段被硬性中断。

应对办法是提前估算并留余量：

```text
并发上限 = min(服务端限额 × 0.7, 本地资源允许的并发)
失败重试 = 只对"重试有效"的类别开启（如限流），其余记录原因后跳过
任务分层 = 必做 / 可延后，跨额度周期执行
```

混合引擎也是这个思路：本机算力打底、云端补量。**本地算力未必快，但它是稳定的、不计次数的**，把长尾和补救批次交给它，额度就能留给真正需要云端吞吐的部分。

::: warning 容易踩的坑
并发数按"想多快"设置，几乎一定会撞上限流。我试过把并发拉满，结果是接口限流、任务互相等待、重试烧掉额度，总耗时反而更长。上限应该从服务端限额倒推。
:::

## 五、失败分类与反馈节奏

失败要分类记录："模型返回格式错误"重试有效，"文件本身损坏"重试一万次也没用。分开之后，最后剩下的 0.04% 每一篇都能一眼看出原因。

反馈节奏也固定下来：超过一分钟的任务，开始前给出预估时长，执行中定期报告进度，失败时说清楚失败在哪一步、已完成多少。这条规范的价值在于——**避免跑了一整晚，早上发现白跑**。

::: tip 性价比最高的一步
从第一版就把"失败原因"当成一等公民分类记录。它几乎不花时间，但把最后的排查从"逐篇看"变成了"按类别处理"。
:::

## 六、可复用的清单

- 状态写到外部文件，会话里不保留唯一副本；
- 用内容哈希之类的唯一键做幂等，替代断点逻辑；
- 并发上限从服务端限额倒推，留 30% 余量；
- 失败按原因分类，只对"重试有效"的类别重试；
- 必做与可延后分开，跨额度周期排期；
- 超过一分钟的任务，先给预估时长，再定期报进度。
