# 让多智能体做硬件设计：一条从拓扑讨论到出货的流水线

> 2026 年 7 月。硬件设计有一个和软件很不同的特点：**出错成本高、反馈周期长**。走完一轮打样要几周，所以"先想清楚再动手"不是风格问题而是成本问题。这个项目尝试把硬件设计流程拆成多智能体可以协作的阶段。

::: info 先说结论
- 阶段化拆解加产物前置，避免设计与布局互相干扰；
- 技能模块化让每个阶段可以单独验证；
- 硬件串行依赖强，多智能体的收益在于每步可验证，而不在并行。
:::

## 拆成阶段，而不是塞进一个会话

流水线分成若干阶段：先讨论拓扑与器件选型，再落原理图，然后做布局布线，最后导出制造文件。每个阶段有明确的输入与输出——**上一阶段的产物是下一阶段的前置条件**，产物不齐就不进入下一阶段。

这样拆的好处是：每次只让智能体关注一个阶段的目标，避免"一边改电路一边改布局"导致的互相干扰；出问题时也能定位到具体阶段。

## 用技能模块而不是一段长提示词

流程被拆成**9 个技能模块**，每个模块负责一类工作（例如器件参数核对、网络表检查、布局约束整理）。模块化的直接收益是**可测试**：每个模块的输出可以单独检查，而不是只能等整个流程跑完看结果。

工具侧通过 MCP 驱动 EDA 软件，让智能体真的能读取与修改设计文件，而不是"给出建议后由人手工操作"。

## 设计了这个流程中最关键的两件事

**一是硬性检查点。** 电气规则检查、器件封装与库存可购性核对这类步骤不允许"看起来没问题就跳过"——它们被写成流程里不可绕过的关卡。硬件不像软件，一个封装错误的代价是整批板子报废。

**二是人工确认的位置。** 流程里明确标出哪些环节必须由人确认后继续（例如最终方案冻结、下单前的 BOM 复核）。把"人该在哪里介入"写进流程，比指望智能体自己判断边界更可靠。

## 与软件流水线的差别

软件项目里，多智能体并行往往能直接换来速度；硬件项目里，**串行依赖太强**，并行的收益有限，重点反而落在"每个阶段的产物是否可验证"。这个项目让我更清楚地看到：多智能体不是万能的加速器，它的价值取决于任务本身能不能被安全地切分。
