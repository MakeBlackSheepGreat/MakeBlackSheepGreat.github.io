# 把一个 Agent 服务放到公网

> 2026 年 9 月。服务在本机跑得好好的，一旦放到公网，问题全都变成了"登录不上"。

::: info 先说结论
- 最费时间的不是"让它能从外面访问"，而是"访问进来之后为什么登不上去、为什么重启一次就失效"；
- 根因很反直觉：**会话密钥是进程启动时随机生成的，不落盘**。进程不重启就没事，托管重启一次，之前发出去的所有凭据全部作废；
- 有些限制在服务端根本没有开关（比如非回环地址下配置只读），那是前端的判断，改不了，只能改部署结构；
- 遇到这类问题，SSH 隧道能立刻"解决"全部症状，但它解决的是症状本身——我没有用它。
:::

## 一、现象：昨天还好好的

服务在本机跑了一个多月，没出过登录问题。交给进程管理器托管之后，第二天打开页面直接提示未授权，清 cookie、换浏览器、换设备都一样。

当时的判断是浏览器缓存或者时钟偏移，试了三条路：

| 试过的方案 | 结果 |
| --- | --- |
| 清 cookie 与站点数据 | 当时能进，第二天又不行 |
| 换浏览器、换设备 | 同样未授权 |
| 检查系统时间与 HTTPS 证书 | 正常，没有偏移 |

按天出现这个规律是破案的关键：不是浏览器的问题，是**服务自己每天重启了一次**。

## 二、根因：进程级随机的密钥

翻配置才看明白：这个服务的会话密钥在**每次进程启动时随机生成，不写盘**。本地用完全没问题——进程不重启，密钥就不变。一旦由进程管理器托管（开机自启、崩溃重拉、定时重启），每次重启都换一把新钥匙，之前签发的会话全部无法校验，表现就是"昨天还好好的，今天打开就是未授权"。

修复很直接：让凭据持久化到固定文件，重启后继续用同一份。

::: warning 容易踩的坑
把服务交给进程管理器之前，先确认它的密钥/凭据是持久化的还是每次启动随机生成的。这类问题在本地永远复现不出来，只有在重启之后才会暴露。
:::

## 三、第二个坑：cookie 作用域

- 会话 cookie 设了 `SameSite=Strict`，意味着**从外部链接跳进来不会带上 cookie**，必须直接在地址栏输入地址打开。这不是 bug，是安全设计，但使用者不知道，只会反馈"点了链接登不进去"。
- 反过来，如果把 `SameSite` 放开、把作用域放宽，等于把自己放进跨站请求伪造的风险里。最后选择保留严格策略，把"请从地址栏直接打开"写进说明。

同一类问题还有一个：服务在非回环地址访问时会主动把一部分配置项变成只读，理由是公网部署下管理员不该通过网页改配置。这个判断完全在前端，服务端没有对应开关，想改也没得改，只能改部署结构。

**评审一个服务的部署文档时，要看它在什么条件下会降级功能**，而不是等上线后某个功能点不动了再去翻源码。

## 四、我为什么没走 SSH 隧道

遇到登录问题，最省事的做法是在本机和服务之间拉一条 SSH 隧道，让公网流量看起来像是从本机发出的——所有"非回环地址"的限制立刻消失，症状全没了。

没有采用。原因有两条：这不是在解决问题，而是把问题藏起来；而且拉隧道等于把一台服务器的安全边界顺势让了出去。最后走的是反向代理加进程托管，把会话问题从根上修掉。

::: tip 性价比最高的一步
部署后先做一次"重启演练"：手动重启服务，再用重启前签发的会话访问一次。这一步几十秒，能把"凭据不持久化"这类只在重启后暴露的问题在交付前抓出来。
:::

## 五、现在的部署长这样

- 服务由进程管理器托管：开机自启、崩溃重拉，日志落到固定位置；
- 凭据持久化，重启不影响已发出的会话；
- 反向代理负责域名与 HTTPS，服务本身只监听本机端口；
- 访问方式写清楚：从地址栏直接打开，不要用转发链接。

回头看，这一整套和"部署一个 AI 服务"关系不大，它就是最普通的运维常识——只是平时自己玩的时候，没人逼你想这些。

## 六、可复用的清单

- 托管前先问：密钥是持久化的还是每次启动生成的？
- 部署后立刻做重启演练，用旧会话访问一次；
- `SameSite=Strict` 会导致外链跳转丢 cookie，这是设计不是故障，写进使用说明；
- 放宽 cookie 作用域换取便利，等于交换 CSRF 风险，不值得；
- 明确哪些功能在非回环地址下会降级，评审时先查这一条；
- 隧道不是修复手段，只掩盖症状，还扩大信任边界；
- 最终形态：进程托管 + 凭据持久化 + 反向代理终止 HTTPS + 服务只监听本机端口。
