# 协作与交付：把要求说清楚，把检查做扎实

> 与智能体协作的产出质量，取决于两件事：**要求说得够不够具体**，以及**验收环节设计得够不够硬**。这两件事都跟模型能力无关，却决定了大部分结果的好坏。

## 一、先说清模式

同一个智能体，在"审查"和"修改"两种模式下的行为完全不同，而它自己不会读心。所以我会显式声明当前模式：

- 审查模式：**只分析、不改动**，输出问题清单与依据；
- 修改模式：按约定范围改动，并给出改动说明。

不声明模式是许多"越改越乱"的起因：它一边分析一边顺手修改，等你回头看时已经分不清哪些是原始问题、哪些是它的改动。

## 二、要求要具体到可执行

| 模糊要求 | 可执行要求 |
| --- | --- |
| 帮我优化一下 | 把首页首屏从 3 个区块减到 2 个，并压缩到一屏内 |
| 检查有没有问题 | 逐页检查外链可达性并列出失效链接 |
| 做得好看一点 | 按这套间距与配色改，改完导出截图给我确认 |

右列的共同点是：**完成与否可以被客观判断**。要求越具体，来回确认的次数越少。

## 三、交付前必须"看得见"

这条是从失败里学到的：一次生成的汇报材料，文件格式、页数、字数全部正确，但排版是错的——因为验收只检查了文件属性，没有人真正看过成品。

由此固定成规则：**生成物必须先渲染出来看，再谈修改**。页面导出截图、幻灯片导出全页图、图表导出成图片——总之要有一个"人能一眼看到"的形态。

这条规则后来被写进项目的规则文件，成为每次交付的必经步骤。

## 四、能自动校验的不要靠人看

反过来，机械性的检查不该消耗人的注意力：链接是否可达、构建是否通过、字数是否超标、资源体积是否异常——这些交给脚本，每次都跑。

分界线很清晰：**机器能判断的交给脚本，必须人判断的（排版、语气、场景适配）由人看，而且真的要看**。

## 五、体会

"和 AI 协作"听起来是关于提示词的技巧，实际上更像是**验收流程的设计问题**。把模式说清楚、把要求写成可判断的形式、把交付物变成可检查的形态，这三件事做到之后，产出质量会稳定得多——而它们在传统软件工程里都有对应物：接口约定、验收标准、交付检查。
