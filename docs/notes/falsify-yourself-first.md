# 先证伪自己：检查失败时的处置顺序

> 2026 年 10 月的一轮站点更新里，核验脚本报了 3 项失败。逐条查完之后发现 3 项全是断言写错，内容一条都没错。这篇记录当时的处置顺序，以及为什么这个顺序值得固定下来。

::: info 先说结论
- 检查失败时，**第一嫌疑人永远是检查本身**，不是被检内容；
- 顺序固定为：取真实文本 → 逐字比对断言 → 才决定改哪一边。跳过后两步直接改内容，是在把正确的东西改坏；
- 同一规则适用于线上异常：一批请求全部失败时，先逐个重试，再判定"服务挂了"；
- 一条失败的检查是问题，不是判决。把它当判决，会引出一次最贵的返工——改坏本来正确的内容。
:::

## 一、三个真实案例

同一轮核验里报了三项失败，三种错法各不相同。

**案例一：词序不匹配。** 断言写的是"已完成的医学影像工作"，页面上的实际文案是"另两项工作已完成并支撑竞赛获奖"。意思一样，语序不同，字符串比对就不过。

**案例二：断言放错了页。** "夺榜挂帅"这个词只出现在获奖页，我却把它写进了经历页的断言。经历页从来没有这个词，断言永远不可能通过。

**案例三：大小写不匹配。** 英文页面的实际文案是"Research swarm system"，首字母大写；断言写的是全小写。浏览器取到的可见文本保留原始大小写，比对失败。

三个案例的共同点：**内容全部正确，断言全部错误。** 如果当时的第一反应是"内容没写对"，回去改文案，会把三段本来正确的文字改坏，而且改完之后还得再改回来。

## 二、处置顺序

失败出现时，按这个顺序走，不要跳步：

| 步骤 | 动作 | 目的 |
| --- | --- | --- |
| 1 | 从构建产物里取真实文本 | 拿到被检对象的确切样子，不靠记忆 |
| 2 | 与断言逐字比对 | 确认差异在哪个字符上 |
| 3 | 差异在断言 → 改断言 | 检查写错，修检查 |
| 4 | 差异在内容 → 改内容 | 真的写错了，修内容 |
| 5 | 两边都说不清 → 停下来问人 | 说明有没搞清楚的前提 |

关键动作是第一步：**从产物里取，不要从记忆里取。** 印象中的文案和实际写入的文案经常差几个字，而这几个字正是失败的原因。取文本要用精确匹配加截取，不要把整篇拉出来肉眼找——长文本里同一个词出现多次，会看错位置。

## 三、同一规则适用于线上异常

这个顺序不止用于断言。那一轮还遇到一次：连续四个线上页面请求全部失败，临时文件也没有创建，看起来就是"网站挂了"。

逐个重试之后，第一个立刻成功，其余三个也全部成功。真实原因是连续快速请求触发了瞬时连接失败，和服务本身无关。

区分两类信号很重要：

- **本地没落盘**：临时文件不存在，后续的读取和统计会连着报错。这类报错说明的是本地写入失败，不是远端无响应；
- **远端真的没响应**：文件创建了，但内容是错误页或空响应。

看到一批失败时，先确认是哪一类，再决定要不要报警。**把本地故障当成线上故障上报，比漏报一次真实故障更损害信誉。**

## 四、什么时候不该修断言

这条规则有边界，不是所有失败都能归给断言。

- 断言描述的是明确约定（"这段旧文案必须消失"），而页面确实还有它 → 是内容错；
- 断言描述的是约定，但约定本身已经变了 → 先确认新约定，再改断言；
- 断言和内容对不上，而两边看起来都讲得通 → 停下来问人，不要挑一个顺手的改。

判据只有一句：**这次改动，依据的是产物里的文本，还是我的记忆？** 依据记忆的改动，一律先回到产物。

## 五、可复用的清单

- 检查失败时，第一嫌疑人是检查本身；
- 顺序：取真实文本 → 逐字比对 → 改断言或改内容 → 说不清就停；
- 从构建产物取文本，不从记忆取；
- 一批线上请求失败，先逐个重试，再判定服务故障；
- 区分"本地没落盘"与"远端没响应"两类信号；
- 依据记忆做的改动，一律先回产物确认。
