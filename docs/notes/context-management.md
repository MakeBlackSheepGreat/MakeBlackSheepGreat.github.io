# 上下文管理：给智能体喂什么信息

> 同一个模型、同一个任务，给的信息不同，产出质量可以差出一个量级。这篇讲信息该怎么分层供给：哪些写进长期文件、哪些随任务走、哪些必须在会话结束前落到磁盘上。

::: info 先说结论
- 信息按四层供给：**系统规则 → 项目规则 → 任务输入 → 会话历史**，越靠上越稳定；
- 规则文件写环境约束，记忆文件写已有结论，两者都不塞进提示词；
- 反直觉的一点：给子任务的信息越多，判断质量越可能下降——它会去"体谅"与它无关的约束；
- 结论只有在得出的当次写进文件才算留下；会话压缩丢掉的通常是过程，但夹在过程里的结论会一起丢。
:::

## 一、一次复核任务：信息给多了，结论反而更差

语料流水线跑到后半段，主会话里已经积累了一堆东西：失败原因分类、调度策略、解析器的边界情况。这时要派一个子任务复核 177 条待审草稿。当时的想法很自然——把主流程的完整上下文一起交给它，"信息全一点总没错"。

现象出现在复核结论上：这批草稿的通过率明显偏低，不少条目被要求重新抽一次。重跑的代价不低：按约 1.3 秒每篇的吞吐，重跑意味着重新排队，而这些额度本该留给 30,031 篇的抽取。

排查时做了一次对照——同一个子任务，只给"条目 + 原文片段 + 判定规则"三项，不带调度历史。两边结论不一致的地方集中在同一类条目上：解析阶段失败过、但正文完整的那些。**子任务看到了失败原因，就把不确定性当成了证据**，把本该转正的草稿判成了待定。结论因此反转：不是信息越多越好，而是越相关越好；供给要分层，与任务无关的历史必须留在原处。

## 二、四层结构

| 层次 | 内容 | 更新频率 | 载体 |
| --- | --- | --- | --- |
| 系统规则 | 角色、输出风格、禁止事项 | 极少变 | 框架配置 / 全局规则文件 |
| 项目规则 | 这个环境与仓库的特殊约束 | 随项目演进 | 项目根目录规则文件 |
| 任务输入 | 这次做什么、验收标准、边界 | 每次任务 | 派发时的任务描述 |
| 会话历史 | 试错与中间结论 | 持续增长 | 会话本身 |

分层的价值在于**越靠上的层次越稳定**：稳定信息写进文件，就不必每次重新交代；临时信息留在会话里，就不必污染长期规则。

## 三、规则文件：写环境的特殊性

规则文件里放的是环境约束，不是项目介绍：

```markdown
## 环境约束
- 本机不装 GPU 版依赖，本地只跑脚本与测试，重计算走远端
- Windows 下路径含空格必须加引号（同一个坑踩过两次）
- 交付前必跑：pytest -q、界面遍历脚本、导出文件哈希核对
```

判断标准很简单：**这条信息不写下来，下次还会踩吗？** 会踩的就写进去。写完的收益是长期的——每次会话开始，等于自动加载一份环境说明书。

::: tip 性价比最高的一步
会话结束前，把这次踩的坑追加到规则文件。写一行的时间，远小于下次重新排查的时间。
:::

## 四、记忆文件：写结论，不写过程

规则文件记录"环境是什么样"，记忆文件记录"我们得出了什么结论"：

- 某个方案验证不可行，以及为什么；
- 某个参数范围确定不适用；
- 某个决定是在什么背景下做的，避免后来者反复推翻。

两类信息只留在会话里，换个会话或换台设备就没了。放进项目目录、用私有仓库同步之后，换框架时真正要迁移的东西很少：**资产在文件里，不在工具里。**

```text
project/
├─ RULES.md     # 环境约束：命令、路径、工具坑、交付前检查
├─ MEMORY.md    # 结论：被否掉的方案、不适用的参数范围、决定背景
├─ tasks.db     # 任务状态：pending / running / done / failed(原因)
└─ notes/       # 阶段性结论与实验记录
```

## 五、子任务只带它需要的输入

**一、按需供给。** 派发时列三样：这次要做什么、判定标准是什么、产出放哪里。把主流程的全部历史带过去，会让它开始为无关约束做取舍——上一节的复核任务就是这么变差的。

**二、不共享可变状态。** 并行的子任务不该改同一份文件；必须改就先串行或先隔离。这一条比上下文长度更容易造成事故。

## 六、长会话：结论要在当次外置

长会话的上下文会被压缩或截断，这是必然的。应对方式是**把重要结论及时外置**：阶段性结论写进记忆文件，任务状态写进任务表，关键决定写进规则文件或项目文档。

原则是：**不要让"只有会话里才知道"的信息成为项目的关键依赖**。会话可以随时丢掉，文件不行。

::: warning 容易踩的坑
压缩时丢掉的多是过程描述，但如果结论只写在过程描述里，它也会一起消失。所以结论要在得出的当次就写下来，并写明判定依据。
:::

## 七、可复用的清单

- 信息分四层：系统规则、项目规则、任务输入、会话历史，按稳定性归位；
- 规则文件只写"不写就会再踩"的环境约束；
- 记忆文件只写结论，附上背景与判定依据；
- 派发子任务时只给输入、判定与产出位置，不带主流程历史；
- 并行的子任务不碰同一份可变状态；
- 每次得出可复用的结论，立刻写进项目文件，不留在会话里。
