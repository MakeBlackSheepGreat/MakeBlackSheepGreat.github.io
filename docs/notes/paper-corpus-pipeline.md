# 把三万篇论文灌进知识库：一次 11 小时的流水线

> 2026 年 8 月。目标很朴素：让文献检索能带着出处。最终跑了 11.2 小时，处理 30,031 篇，完成率 99.96%。真正难的不是模型，而是让这条流水线在几万次重复里不出错。

::: info 先说结论
- 最反直觉的一条：**并发拉满反而更慢**。第一版把并发开到最大，上游模型服务被打爆，请求全卡在超时上；按服务端限额倒推并发之后，总耗时反而降了；
- 幂等不要靠"我处理到第几个了"，靠**内容哈希**——每篇先算哈希，见过就跳过，重跑天然安全；
- **失败原因要和失败状态一起记**。最后 0.04% 难查，不是因为失败多，而是因为第一版只记了 failed，没记为什么 failed。
:::

## 一、要解决什么

文献检索最容易出的问题是"讲得头头是道，但找不到原文"。这次要做的事很具体：把本地 PDF 目录跑一遍，抽出可检索内容落成知识条目，每条都能点回原文的具体位置——不是"这篇论文说过"，而是"这句话来自这篇的第几段"。

目录里共有 30,031 篇。跑之前的估算是：按每篇几秒算，这是一次 10 小时量级的长跑。所以设计前提不是"一口气跑完"，而是"中途一定会断"。

## 二、第一个坑：并发拉满，反而更慢

第一版把解析、分块、推理、落库串成一条线，并发开到最大。前 20 分钟很快，之后逐渐变慢，日志里出现大量超时重试，同时上游服务的响应时间从几百毫秒涨到十几秒。

原因不复杂：并发上限是我按"本机还能扛多少"定的，上游有自己的限流和排队，超出的请求只是在队列里等超时，超时后又被我重试了一遍，把负载进一步放大。

改法是反过来算：先测上游在稳定响应下的处理速率（约 1.3 秒/篇的吞吐就是这么来的），把并发压在这个速率之内，本机只负责缓存和落盘。改完之后单篇延迟稳定，总耗时短了。

::: warning 容易踩的坑
并发上限要从**服务端限额**倒推，而不是从"我想多快"决定。本地脚本的并发能力和上游的处理能力是两件事，前者开大只会把压力变成超时。
:::

## 三、第二个坑：失败只有一个状态

跑完 99.96%，剩下 0.04%。按理说可以收工了，但收尾花了不少时间——因为第一版的任务表里只有一个 `failed`。

实际至少有两类失败：**模型返回格式不对**（重试一次大概率能过）和**文件本身有问题**（重试一万次也没用）。混在一起导致重试策略无法分层：全都重试会白烧额度，全都不重试会漏掉本该成功的那批。第二版把原因拆开记录后，剩下的每一篇都能一眼看出属于哪类。

::: tip 性价比最高的一步
把"失败原因"当成一等公民字段，从第一版就分类记录。一行字段，换掉几小时的逐篇排查。
:::

## 四、第二版：任务表加内容哈希

重跑的成本也必须压下去，因为中断是常态——11 小时里网络中断过 1 次。第二版把状态全部外置：

```text
tasks.db
  paper_id | status | reason | updated_at
  ---------|--------|--------|-----------
  ...      | pending / running / done / failed(reason)
```

进程重启后不做任何"续传"判断，直接读表继续。幂等则交给内容哈希，与进度无关：

```python
h = content_hash(pdf_path)
if table.seen(h):
    return                      # 重复执行天然安全
table.enqueue(h, pdf_path)
```

两个设计合起来，让"重跑"从需要小心操作的事变成随便做也没关系的事：网络中断后它自己接着跑完，没有人工介入。

## 五、混合引擎要分工，不是谁快用谁

推理用了两种资源：本机显卡跑小模型，云端负责长文和补救批次。最初的调度规则是"谁空闲谁上"，结果把长文丢给了吞吐有限的本机，把短文本送上了按篇计费的云端，两边都不划算。

改成按论文特征分工之后规则才稳定：结构清晰、长度短的走本机，长文和解析失败的批次走云端。**混合引擎的价值不是更快，而是不被单一资源卡死**——本机排队时往云端放，云端限流时本机继续跑。

## 六、结果

| 指标 | 数值 |
| --- | --- |
| 论文总数 | 30,031 篇 |
| 完成 | 30,018 篇（99.96%） |
| 总耗时 | 11.2 小时（约 1.3 秒/篇） |
| 知识条目 | 102 条正式条目 |
| 证据链接 | 18,125 条 |
| 待审草稿 | 177 条 |
| 中途故障 | 网络中断 1 次，自动续跑完成 |

还有一条克制：抽出来的内容不能直接当结论，一部分进了待审队列（177 条），人工复核后才转正。自动化能把吞吐拉起来，但**该人看的地方还是得人看**。

## 七、可复用的清单

- 幂等用内容哈希，不维护"处理到第几个"的游标；
- 任务表是唯一事实来源，重启后只读表，不做续传判断；
- 失败状态和失败原因分开记，从第一版就分开；
- 并发上限从服务端限额倒推，不从本地能力倒推；
- 混合推理按任务特征分工，不按"谁空闲"；
- 先跑通一篇的端到端质量检查再接并发——质量问题是批量的，发现得越晚越贵。
