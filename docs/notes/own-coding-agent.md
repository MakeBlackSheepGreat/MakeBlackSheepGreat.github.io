# 把自己的编码智能体做成一件长期作品

> 2026 年 6–9 月。动机很直接：现成的编码智能体在"通用"上做得很好，但想要的几样东西——持久记忆、以中小型模型驱动的多智能体工作流、目标驱动的长任务执行——要么没有，要么不可控。

::: info 先说结论
- 从零写是弯路：真正耗时间的不是核心循环，而是文件编辑、命令执行、上下文压缩这些"重复造"的部分；
- 最后走的是**增量改造**——在开源底座上只移植 9 项真正需要的特性，上游升级时冲突面最小；
- 客户端协议按**任务语义**设计：移动端定了 agent-bridge 的 21 个请求与 18 个事件，而不是套用现成的移动端规范。
:::

## 一、从零写了两周之后改主意

起点是一个很具体的需求：要一个能自己跑长任务、并且记得住结论的编码智能体。最初的想法是重写——只有全部自己写，才谈得上可控。

两周之后的状态很不好看。时间几乎全花在底座功能上：多文件 patch 与冲突处理、命令执行与超时、上下文压缩、失败重试。每一项都能跑，但每一项都不如成熟实现稳，而"记忆""目标驱动"这些真正想要的东西一行没写。

转机是换了一条判据：不再问"是不是我写的"，改问"**能不能在不 fork 上游的前提下，把要的行为加进去**"。答案是可以，于是改成增量改造。

## 二、9 项特性的取舍

把想要的特性列成清单，只保留"上游确实没有、且至少被用到 3 次"的项，最后一共保留 **9 项**，其余保持上游结构。补上的能力分三类：

- **持久记忆**：跨会话保留结论与约束，而不是每次重新交代；
- **多智能体工作流**：面向中小型模型设计分工，让便宜模型也能完成需要多步推理的任务；
- **目标驱动执行**：给一个目标，让它自己拆解、推进、中断后续跑。

记忆条目落地成文件，按项目分片，结构固定到可以直接 `diff`：

```json
{
  "scope": "project:site",
  "key": "docs-build",
  "value": "改侧边栏后必须跑一次构建；只改正文可跳过",
  "source": "session-2026-07-14",
  "created_at": "2026-07-14T21:03:00+08:00"
}
```

写入时机固定在三个位置：任务收尾、失败分支、人工纠正。这样做的收益是可维护——上游更新时冲突集中在自研的 9 项上，出问题也容易分清是自研部分还是底座。

## 三、客户端协议：为什么否掉了现成的移动端规范

为移动端做了一套 agent-bridge 协议：**21 个请求、18 个事件**。设计过程中有一次作废值得记下来。最初的方案是直接套用一套现成的移动端设计规范，做到一半否掉了。

原因是现象摆在面前：终端类 agent 的交互语义是流式输出、长任务、可中断可续跑，而常规移动应用的状态模型里，"正在输出但已停止接收""任务已中断但可以续""会话已恢复但历史被截断"这三种状态会被挤进同一个"加载中"的壳里。界面上看不出区别，用户只能靠猜。

改法的核心是**状态机写进协议**，客户端只负责展示：

| 类别 | 数量 | 覆盖内容 |
| --- | --- | --- |
| 请求 | 21 | 建会话、派任务、读写文件、查询记忆、审批确认等 |
| 事件 | 18 | 流式输出、任务进度、中断、恢复、错误、额度提示等 |

协议里把"中断"和"失败"分开定义，是这次设计里最实用的一条：中断是可续的正常状态，失败才需要人来处理。

## 四、发布与文档

项目发布到 npm，带版本号与变更记录；另配一个独立文档站（VitePress，中英双语，主站加镜像两条部署路径）。文档站不是装饰：把"为什么这样设计"写清楚，下次自己要改的时候能省一半时间。

## 五、顺带补上的两块基础设施

**模型服务**：为自托管推理写过一个 vLLM out-of-tree 插件，把某模型族的模型实现、Transformers 配置与工具调用解析器以插件形式接回框架，**不改动上游源码**。选择插件而不是打补丁的理由很实际：补丁在框架升级时必然冲突，而插件的接口是框架承诺过的。

**随身入口**：把自建的一组网页服务聚合成一个安卓应用（Flutter），手机上可以直接访问自己的服务，不必记住一堆地址和端口。

::: tip 性价比最高的一步
动手改造前先打一个基线 tag，并让自研改动与上游代码在提交历史里保持可区分。自举开发（用它改它自己）时，这一步是唯一的回退路径。
:::

::: warning 稍加注意
"只移植真正被用到的特性"是为了控制长期维护面。清单越长，上游升级时的冲突越多；每加一项，都应该能说出它被谁用到、用了几次。
:::

## 六、可复用清单

- 先问"上游能不能加"，能加就做增量改造，不轻易 fork；
- 特性清单按"被使用次数"筛，不按"看起来有用"筛；
- 记忆写成文件、按项目分片、写入时机固定，保证可读可 diff；
- 协议按任务语义定义状态（尤其是中断与失败要分开），不套用通用界面规范；
- 发布与文档一起做：版本号、变更记录、独立文档站；
- 自举改动前打基线，永远留一条回退路径。
