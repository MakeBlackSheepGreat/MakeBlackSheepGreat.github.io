# 第一次在算子层写代码

> 2026 年 8 月。参加国产 AI 芯片的算子题目：二维卷积、激活函数、量化 GEMM，以及一个"消除末维上限"的实现。在此之前，我写的都是"调用"算子的代码。

::: info 先说结论
- 算子层的性能不来自更聪明的技巧，而来自**把数据搬运的次数降下来**。分块策略比任何微优化都重要；
- 第一版编译不过的原因是地址空间标注错误——在模型层，数据在哪块内存是框架的事；在算子层，它由你决定；
- 一个"简单"的激活函数要处理三种数据类型和九种维度组合，靠"跑一遍看看"是覆盖不完的，必须逐个分支想清楚。
:::

## 一、从"调用"到"实现"的落差

模型层的写法是把数据搬到设备上，然后调用现成的算子；算子层要回答的问题完全不一样。第一次上手时，最直观的三个变化是：

- **地址空间是显式的**：这段内存属于全局、共享还是寄存器，需要自己标注并决定数据在哪一级之间搬运；
- **分块决定性能**：同一份计算，按不同方式切分输入与输出，性能可以差出好几倍；
- **类型逐分支处理**：FP16、FP32、BF16 各写一遍，维度和形状的组合也要逐个覆盖。

## 二、第一次编译失败：地址空间标错了

第一版代码编译没过，报错指向某段缓冲区所在的地址空间不匹配。当时的直觉是"数据反正在内存里，标不标有什么关系"——在模型层这个直觉是对的，在算子层它直接决定了数据要不要跨级搬运、以及能不能被计算单元读到。

改对之后才理解了它的意义：**地址空间标注不是形式约束，而是让"搬运"这件事显式出现在代码里**。也正因为显式，才能看出哪些搬运是多余的。

## 三、分块的反转：切大不一定更好

按"让每个块尽量大、减少循环次数"的思路，我先把分块调大。结果性能反而下降。原因是片上缓存容量有限：块大到装不下，就要反复从外部存储回读数据，循环次数少了但搬运次数多了。

于是判断标准从"块大不大"换成了"同一份数据被搬了几次"。围绕这个问题重新设计分块之后，性能才稳定下来。这次之后我形成一个习惯：**性能问题先看数据复用，再看指令和技巧。**

::: tip 性价比最高的一步
动手调优之前，先画出"每块数据从哪个层级搬到哪里、被复用几次"的路线。这张图画出问题，优化方向基本就定了；画不出来，说明还没理解自己的实现。
:::

## 四、几道题，和它们真正的难点

| 题目 | 真正的难点 |
| --- | --- |
| 二维卷积（FP16 / FP32 / BF16） | 三种数据类型分别实现，并各自选择分块策略 |
| 逐元素激活（HardSwish，0–8 维） | 维度分支与形状对齐，避免小形状上的性能退化 |
| INT8 量化 GEMM（小 M/N、大 K） | 量化参数处理与累加精度，K 维分块 |
| 消除末维 65535 上限 + 转置组合 | 突破单次搬运的形状限制，并处理转置后的访存模式 |

HardSwish 这道题最容易被低估：它算起来简单，但要覆盖 0 到 8 维的不同形状，还要保证小形状下不退化成逐元素逐个算的慢路径；量化 GEMM 的难点则在精度——整数与浮点混合计算时，累加的方式决定了结果还能不能对得上。

## 五、消除末维上限那道题

某次搬运的末维长度有 65535 的限制，超过就直接失败。这是硬件规定的形状约束，改不了硬件，只能改数据的组织方式：把超长的末维拆成若干段分别搬运，在计算侧再组合回来。

麻烦的地方在于拆分之后访存模式变了——原本连续的一段变成多段，如果按顺序处理，访存效率会掉下来；如果配合转置，又要额外处理转置后的布局。最后的实现是两者组合，先按限制切分，再选择转置来保持访存的连续性。

::: warning 容易踩的坑
遇到硬性形状限制，第一反应往往是"能不能绕过去"。多数情况下绕不过去，能做的是把数据重新切分，并承担切分带来的访存代价——这个代价必须提前算进去，否则切完反而更慢。
:::

## 六、一点体会

最大的收获不是学会某个写法，而是**对"性能从哪来"有了具体的感知**：不是靠更聪明的技巧，而是靠把搬运次数降下来。这个视角反过来影响了我做模型训练时的判断——在显存受限时如何设置批次与分块，本质上是同一件事。

## 七、可复用的清单

- 先确认地址空间与数据流向，再写计算逻辑；
- 性能先看数据复用次数，分块不是越大越好；
- 每种数据类型、每种维度组合都要单独过一遍，不靠试跑覆盖；
- 遇到硬件形状限制，先考虑切分与布局调整，而不是寻找绕过的方法；
- 量化算子的精度问题优先查累加方式；
- 把"数据从哪搬到哪、搬了几次"画成图，再谈优化。
