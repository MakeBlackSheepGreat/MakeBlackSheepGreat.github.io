# 一个人怎么带一群 Agent

> 我经常同时开着好几个 AI 编程助手干活：一个负责查代码找原因，一个负责改，一个专门挑毛病，还有几个在跑互不相干的实验。带了半年多，有几条经验是用失败换来的。

::: en Abstract
Practical lessons from running multiple coding agents at once: how to split roles, how to keep long-running tasks recoverable, and how to write acceptance criteria that an agent cannot quietly talk its way around.
:::

## 角色要分开，而且不能是同一个"脑子"

把所有事都交给一个智能体，它会在"实现"和"审查"之间反复摇摆：自己写的代码，自己倾向于认为没问题。分开之后就简单了——探索的只做只读检查、给出结论；实现的不做验收；审查的带着检查清单去挑问题，并且明确要求它**不许改代码**。

角色分工真正的价值不是并行，而是让"提出方案的人"和"验证方案的人"不是同一个。

## 长任务必须能续跑

超过一小时的任务，我一定会要求三件事：

1. **进度落盘**——做到哪一步、哪些完成了、哪些失败了，都写进文件，而不是只留在对话里
2. **预估时长**——开始之前先估一个时间，超过一分钟的任务要告诉我大概多久
3. **断点续跑**——被中断之后重新启动，要能接着上次的位置继续

这三点听着像废话，但缺了任何一条，长任务都会变成"跑一晚上，第二天发现白跑"。

## 验收标准要机器可判

"改得好看一点""检查一下有没有问题"这类要求，等于没提。有效的验收标准长这样：

- 全部测试通过，且给出通过的条数
- 页面的每个可点击元素都被真实点击过，报告点击总数和失败数
- 导出的图片必须实际渲染出来看过，而不是只检查文件存在

最后一条尤其重要：文件存在、XML 合法、字数对得上，都不代表交付物是对的。**能自动检查的部分交给脚本，只有人能判断的部分（排版、语气、是否符合场景）才交给人，但必须真的看一眼。**

## 记忆要写在文件里，不要留在对话里

同一个坑踩第二次的时候，问题不在能力，在流程。所以每个项目我都会维护一份规则文件，把"这个环境的特殊性"写进去：什么命令不能用、哪个路径要转义、哪些工具在这个机器上是坏的。

这些东西写一次，后面所有会话都受益；不写，每次都要重新踩一遍。

## 别把并发拉满

我试过同时派十几个子任务，结果是：接口限流、相互等待、失败重试把配额烧光。后来改成先缓存结果再并发消费、给并发数设上限、失败的单独排队重试——总耗时反而更短。

## 一句话总结

把 Agent 当成一群能干但需要明确指令的实习生来管理：任务描述要具体，验收标准要能验证，进度要可见，踩过的坑要写进制度。做到这几条，一个人确实能同时推进很多事。
