# 技术笔记

记录工程实践中的问题定位与方案取舍，以及长期使用智能体后形成的方法。内容基于实际项目，具体到可复现的程度，不涉及私有信息。

## 一、智能体协作方法

这一组是我用了一年多智能体之后沉淀下来的做法，与具体框架无关。

- [一年里我用了四套智能体框架：数据复盘](/notes/agent-frameworks-retrospective) —— 用会话记录反查自己的判断：迁移的真实触发点、被误读的会话数、以及跨框架唯一不贬值的资产
- [把问题拆成智能体能执行的任务](/notes/task-decomposition) —— 四层拆解（目标/判定/子任务/执行单元）、拆之前要回答的三个问题、粒度与串并行判断，以及三种常见的拆解错误
- [AI 时代的工程能力：什么在贬值，什么在升值](/notes/skills-in-agent-era) —— 一条可操作的判据（对错能否自动判断）、七项在升值的能力、以及面向 Agent 时代的技能清单
- [上下文管理：给智能体喂什么信息](/notes/context-management) —— 四层信息供给、规则文件与记忆文件各写什么、子任务上下文要干净、长会话如何外置结论
- [多智能体分工：角色、并行与验收](/notes/multi-agent-roles) —— 角色拆分的价值不在并行，而在让提出方案的人不负责验证；以及并发上限、失败分类与可判断的验收标准
- [长任务的工程化：进度、预算与中断恢复](/notes/long-task-engineering) —— 进度落盘、幂等续跑、预算与限流预估，以及"中断是常态"这一设计前提
- [记忆与规则：把踩过的坑变成制度](/notes/memory-and-rules) —— 项目规则文件、跨会话记忆、需求总账，以及"下次是否会自动起作用"这条判断标准
- [协作与交付：把要求说清楚，把检查做扎实](/notes/collaboration-and-delivery) —— 显式声明审查/修改模式、把要求写成可判断的形式、交付物必须先"看得见"
- [工具选型与迁移：一年换过多个框架之后的标准](/notes/agent-tool-selection) —— 评估维度、何时该换与何时不换、何时自研，以及"真正的资产不在框架里"
