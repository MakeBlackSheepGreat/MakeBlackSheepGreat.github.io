# WeftMesh：让每台设备都是完整的智能体

> 2026 年 9 月。出发点是一个很日常的困境：笔记本、服务器、NAS 与手机上各装了一套智能体，但它们各自为战——每台设备都要单独配置、单独给凭据、单独看进度，跨设备协作只能靠人来回搬。

::: info 先说结论
- 拓扑选了星型而不是全互联：不是性能考虑，而是**两两维护关系会在设备上下线时产生状态冲突**，集中到一点反而简单；
- 跨设备执行代码意味着权限必须默认关闭、按设备授权；
- 反直觉的一点：**断线恢复要按正常路径设计**，而不是当成异常处理。手机切网、服务器重启都是日常事件，"重连"其实是主流程的一部分。
:::

## 一、最初想做全互联

最初的想法是让每台设备都和其余设备直接建立连接：任两台之间都能通信，看起来最灵活，也不存在单点。

真做的时候冲突很快出现：设备 A 与设备 B 各自维护的"对方状态"在上下线时会不一致——手机切了一次网，A 认为它在线、B 认为它离线，两边都按自己的判断派发任务，同一个任务被发下去两次。而设备数量一多，"每台设备维护与其他所有设备的关系"这件事的组合数增长得很快，每加一台设备都要让所有人知道。

## 二、改成星型：状态与鉴权集中到一点

最后的拓扑是一台设备作为枢纽，其余设备接入。这样做的直接收益是**状态与鉴权只有一份**：谁在线、谁有什么能力、谁被授权，都由枢纽维护，设备之间不需要两两同步，上下线也不会产生互相矛盾的判断。

设备之间用自研的轻量协议通信，只处理三件事：

```text
① 能力声明  这台设备提供什么：GPU、容量、已装工具
② 任务分发  枢纽派发 → 设备执行 → 结果回流到原会话
③ 状态恢复  断线后重新对齐，而不是重置
```

枢纽本身不是特权设备，它只是连接关系的中心——业务逻辑仍在发起任务的那台设备上。

## 三、权限：默认关闭，按设备授权

"借用彼此的环境"意味着可执行代码可以在设备之间流动，这是这个项目里风险最高的一处设计。原则定得很硬：

- 能力开放**默认关闭**，每台设备单独授权；
- 任务来源必须可验证，不能由任意一端伪造；
- 一台设备能被调用的能力范围，由提供方声明，而不是由调用方指定。

::: warning 容易踩的坑
跨设备执行代码最容易被忽略的不是传输加密，而是**授权边界**：一旦某台设备被允许执行任意代码，它就不再是"我的另一台电脑"，而是整个网络里的一个执行节点。默认关闭不是保守，是这类系统的必要默认值。
:::

## 四、断线是常态，不是异常

第一版把断线当异常处理：连接断了就清理该设备的状态，等它重新接入时按新设备注册。结果是手机切一次网，正在跑的任务结果回不来，重新接入后上下文全丢。

改成把恢复当正常路径之后，行为变得可预期：设备重新接入时带着自己之前的身份和未完成任务的状态，枢纽对齐双方认知后再继续派发。这和"重连等于重新开始"是完全不同的两件事。

::: tip 性价比最高的一步
在写任何调度逻辑之前，先把"一台设备重新接入时，双方各自知道自己什么、不知道什么"列成一张表。断线恢复的复杂度几乎全部来自这张表没写清楚，而不是来自协议本身。
:::

## 五、目前的状态

- 三平台支持：Android、Linux、Windows；
- **176 项测试通过**，覆盖协议编解码、任务分发、断线恢复与权限校验；
- 定位是可用原型，不是成熟产品——README 里直接写明"现在能做什么"与"还不能做什么"。

## 六、一点体会

这个项目最大的收获不在协议本身，而在于**把分布式系统的基本约束用在了个人环境上**：网络会断、设备会重启、凭据会过期、并发会互相干扰。这些在单机使用智能体时几乎不会遇到，但只要跨出一步就必须正面处理。

## 七、可复用的清单

- 拓扑选型先看状态一致性成本，再看性能；
- 状态与鉴权集中到一点，比让每台设备维护全部关系更简单；
- 代码可以跨设备流动时，能力默认关闭、按设备授权、来源可验证；
- 断线恢复走正常路径，不清理上下文、不按新设备注册；
- 设备只声明"我能提供什么"，其余交给调度，不追求能力镜像；
- 原型阶段就把"能做什么/不能做什么"写进 README，避免被当成产品使用。
