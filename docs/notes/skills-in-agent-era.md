# AI 时代的工程能力：什么在贬值，什么在升值

> 这半年我用多套智能体框架做过真实项目：科研工作流、语料处理、服务部署、硬件设计流水线。做这些事的过程里一直有个问题没有绕开——AI 已经能读汇编、能独立改代码、能自己跑实验之后，工程能力的价值发生了什么变化？

::: info 先说结论
- **贬值的是"写"，升值的是"定义与验收"**；
- 判断一项能力会不会被替代，有一条可操作的判据：**这件事的对错能不能被自动判断**；
- 一个容易被忽略的对称性：AI 把产出速度提高 N 倍，也把返工速度提高 N 倍，净收益取决于验收环节做得多扎实；
- 工程能力不会像手写汇编那样过期，但它的作用点从"自己实现"变成了"定义约束 + 审查产出"。
:::

## 一、一次界面交付：时间花在了哪里

2026 年 8 月的医学影像软件要求刻盘交付，运行环境不由我控制。界面有 13 个页面、265 个可点击元素。按习惯，第一反应是自己点一遍——人工点完要半天，而且点漏了不会知道。

这件事最后交给了自动化测试：驱动真实的桌面应用遍历界面，逐一审计可点击元素、执行点击、记录失败。结果是审计 265 个元素、实际执行 192 次点击、零失败。写脚本花的时间比人工点一遍还少，而且结果能直接写进交付说明："零失败"比"检查过了"有说服力。

分界线也出现在这里：脚本覆盖的是"点下去不报错、界面不崩"，"这个按钮的业务逻辑对不对"仍然必须由人判断。于是把两类检查分开——脚本负责覆盖面，人负责抽查关键流程。**同样的能力，用在"写页面"上的部分在贬值，用在"定义点哪些、判定什么叫失败"上的部分在升值。**

::: tip 性价比最高的一步
把"什么算通过"写成一个脚本，再交给智能体执行。做完这一步，验收不再依赖谁记得去检查，而是每次跑完都给出一个数字。
:::

## 二、判据：对错能不能被自动判断

| 工作的性质 | 交给谁 | 原因 |
| --- | --- | --- |
| 对错可自动判断（测试通过、指标达标、构建成功） | 智能体 | 有客观反馈，它能自己收敛 |
| 对错只有人能判断（需求是否合理、结论是否成立、体验是否可接受） | 人 | 没有反馈信号，它会自信地走错方向 |

按这条判据，"会写代码"本身正在贬值，而**定义"什么算写对了"**在升值。它也解释了为什么同样上 AI，有的团队效率明显提升，有的只是产出更多返工——差别不在工具，在第二行那一栏有没有人认真做。

## 三、在贬值的东西

- **敲代码的速度**：最直接被替代的部分；
- **样板式实现**：CRUD、配置、脚手架、常规测试，模型写得又快又稳；
- **对单一工具 API 的记忆**：模型比你记得准；
- **"知道怎么写"这类记忆型知识**：查得到的东西，价值迅速下降。

## 四、在升值的七项

| 能力 | 为什么它替代不了 | 具体动作 |
| --- | --- | --- |
| 问题定义 | 需求侧的判断，没有客观信号 | 把"优化一下"变成"首屏区块从 3 个减到 2 个，1280×720 内不出现滚动" |
| 验收设计 | 验收标准决定协作质量 | 写成可执行的检查项：测试条数、点击计数、指标阈值 |
| 系统与接口设计 | 接口清楚才能并行，模糊只会制造冲突 | 先定接口，再分头实现 |
| 领域判断 | "该不该做这个方案"依赖对领域的理解 | 提前砍掉不值得做的方向 |
| 上下文组织 | 喂什么信息直接决定判断质量 | 分层供给，见[另一篇笔记](/notes/context-management) |
| 成本与预算 | 哪些环节贵、并发上限设多少是工程经济学 | 长任务先估额度与限流，再决定并发 |
| 审查与故障定位 | 产出变多后，"哪里不对"成为瓶颈 | 机械检查交给脚本，注意力留给"为什么不对" |

这七项里，前三项在[拆解那篇](/notes/task-decomposition)里展开过；领域判断这一项，最省时间的用法不是"想出更好的方案"，而是提前否掉一个不该做的方案——一次消融实验把准确率从 77.23% 拉到 56.78%，第 61 个 epoch 崩坏，因为判定门槛写在实验之前，这个方向两天内就被停掉，没有拖成几周的调参。

## 五、AI 会写代码之后，还需要什么能力

结论是：工程能力不会过期，但形态变了。

- **起作用的方式变了**：过去是"我来组织代码"，现在是"我定约束、它来组织、我审查结果"；
- **要求反而更高**：产出速度提升 N 倍，如果不给结构，制造混乱的速度同样提升 N 倍，而结构只能由人给；
- **不会自动获得**：这些能力只在真实项目里长出来，跳过实践过程也就跳过了能力形成的过程。

::: warning 容易踩的坑
把实验课交给 AI 一键完成，损失的不是"没学到某个 API"，而是**失去了从模糊需求走到可验证方案的完整过程**。恰好这一段是 AI 替代不了、也只能靠自己做一遍才能学会的部分。
:::

## 六、可复用的清单

- 拿到任务先分类：对错能自动判断的交给智能体，只能人判断的自己留下；
- 能自动判断的那一类，先把检查写成可执行的脚本，再交给智能体；
- 只人判断的那一类，不要外包，也不要指望"看一眼觉得还行"；
- 方案层提前做减法：不值得做的方向越早砍掉越省；
- 产出量上来之后，把机械检查全部脚本化，人的注意力只留给故障定位；
- 遇到不可逆操作、或者自己都没想清楚的事情，先不用 AI。
