# 多智能体分工：角色、并行与验收

> 同一件事交给一个智能体，还是拆给几个智能体？这一年里两种做法我都长期跑过，结论是：**拆分的价值不在并行，而在让"提出方案的人"和"验证方案的人"不是同一个**。

## 角色怎么分

我实际在用的分工是三类：

| 角色 | 只做什么 | 明确不做什么 |
| --- | --- | --- |
| 探索 | 只读检查、给出结论与依据 | 不改任何文件 |
| 实现 | 按约定范围改动代码 | 不做自己的验收 |
| 审查 | 按检查清单找问题 | **不许改代码** |

三条里最关键的是"审查者不许改代码"。一旦允许改，它就会倾向于把问题就地修掉，于是"发现问题"这个环节消失，剩下的只是"另一个实现者"。

## 并行不是越多越好

我试过一次派出十几个子任务，结果是限流、互相等待、重试把额度烧光，总耗时反而更长。后来固定成三条：

1. **先缓存再并发**：结果先落盘，重跑几乎零成本；
2. **给并发设上限**：按接口限额倒推，而不是按"想多快"决定；
3. **失败分类重试**：区分"重试有效"与"重试无用"（如接口限流 vs 输入本身有问题）。

## 验收标准要机器可判

"检查一下有没有问题"这类要求等于没提。可用的验收标准长这样：

- 全部测试通过，并给出通过条数；
- 界面每个可点击元素都被真实点击过，给出点击与失败计数；
- 导出的图片必须实际渲染出来看过，而不是只确认文件存在。

第三条最容易被忽略：**文件存在、格式合法、字数对得上，都不代表交付物是对的**。

## 子任务要能独立判断完成

每个子任务必须自带"什么算做完"，否则主流程无法判断该收还是该等。我给长任务的标准是：进度落盘 + 明确产出物 + 超时与重试策略，三样齐了才发出去。

## 一点体会

多智能体协作的收益不在"更快"，而在于**把校验环节从人的注意力里解放出来**：人可以只在关键节点看结论，而不是全程盯着每一步。
