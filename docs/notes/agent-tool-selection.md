# 工具选型与迁移：半年换过多个框架之后的标准

> 半年里在本机长期使用过四套智能体框架，也自己改造过一个。外界看是"换得很勤"，但每次迁移背后都是同一个问题：**当前框架的能力边界，是否已经挡住手上的任务类型**。

::: info 先说结论
- 迁移的真实触发点是**任务类型变了**，不是"出了新工具"；四套框架并存、按任务类型分工，比"选一个最好的"更实际；
- 最反直觉的一条：**迁移成本被系统性低估**。第一次迁移原以为是一小时的配置复制，实际花了三天——要重建的是规则文件、记忆和已脚本化的工作流；
- 真正的资产是**规则文件、记忆文件、验收习惯**，它们必须放在框架之外，否则每换一次框架就要重建一遍。
:::

## 一、一次被低估的迁移

2026 年 6 月，我从一套框架换到另一套，计划是"下午弄完"：配置文件复制过去，路径改一改，收工。

实际列的清单是这样：

| 要搬的东西 | 原以为 | 实际 |
| --- | --- | --- |
| 配置文件 | 复制粘贴 | 字段名与语义不通用，逐项对照翻译 |
| 项目规则 | 没想到 | 每个项目的环境约束（哪些命令不能用、哪些路径要转义）要重写一遍 |
| 记忆 | 没想到 | 半年的结论散在会话记录里，得人工捞 |
| 常用流程 | 没想到 | 已经脚本化的几个工作流要在新框架里重新封装 |

实际耗时三天。第二次迁移之前先做了一件事：把规则与记忆从框架里搬出来，落到项目目录下。到第三次迁移时，这部分的投入是零——只写了一段"怎么读取这些文件"的入口说明。

## 二、评估维度：别问"支持不支持"，要问"跑到第几小时会断"

选型对比表里最容易失效的字段是"支持 / 不支持"。把每个维度改写成可判断的问法之后，判断才稳定：

| 维度 | 可判断的问法 |
| --- | --- |
| 上下文容量 | 一个 8,000 行的文件加 200 条历史，能不改写地读进去吗 |
| 长任务能力 | 无人值守连续跑 3 小时，中途断了能不能自己续上 |
| 多智能体 | 派 10 个子任务，各自独立完成并回传，还是互相等待 |
| 可扩展性 | 能不能接入 MCP、插件、技能，而不只是靠提示词 |
| 可控性 | 能不能指向本地模型或自建服务 |
| 成本模型 | 长跑时按什么计（按次、按量还是按时长），限流在哪一档 |

## 三、什么时候换，什么时候不换

触发迁移的从来不是"出了新工具"，而是任务类型变了、旧框架没有对应机制。半年里真实的触发点只有三类：需要无人值守跑几小时的自主任实验；需要在超大仓库上工作；需要把子任务成批派出去。

反过来，有三种情况即使新工具更好也不换：

- **增量收益小于迁移成本**——按上一节那张表估算，而不只算配置文件；
- **旧项目仍在进行**——让旧项目在原框架里跑完，新任务再用新框架；
- **只是"更流行"**——社区热度不代表能力边界发生变化。

::: warning 稍加注意
用使用量指标（会话数、工具调用次数、使用时长）判断框架好坏，会系统性高估短问答型的使用。翻使用记录时发现，记录里有一批并不是人与模型的对话，而是主流程派发出去的子代理线程；按会话数排出来的"最常用框架"和产出最多的框架并不是同一个。
:::

## 四、什么时候自研

只有当需要的能力**上游不可能提供**时，自研才有意义——因为它是项目特定的，或者上游在同样的地方做了不同取舍。

做法是增量改造而不是重写：以开源实现为底座，把想要的特性写成清单，只移植真正需要的（最后保留 9 项），其余保持上游结构。这样上游升级时冲突面小，出问题也容易分清是"自己加的那部分"还是"底座的问题"。

## 五、真正的资产不在框架里

半年下来最重要的一条结论：**记忆、规则、方法论不应该存放在任何框架内部**。它们以文件形式存在于项目目录中，框架只是执行层，随时可以替换：

```text
project/
├─ AGENTS.md            # 环境约束：什么不能用、什么要转义
├─ docs/decisions/      # 结论与取舍：为什么这么做、被否掉的方案是什么
└─ scripts/check.sh     # 验收习惯：交付前固定跑一遍
```

这样看，"换了几个框架"本身并不重要——重要的是每次迁移时，真正的资产没有被留在身后。

::: tip 性价比最高的一步
迁移之前先做这一步：把规则文件与记忆从框架里搬到项目目录，新框架里只保留一段"怎么读取它们"的入口说明。做完之后，迁移就从"重建"变成了"接入"。
:::

## 六、可复用清单

- 换之前先确认一件事：这类任务在旧框架里有对应机制吗；
- 迁移成本按"规则 + 记忆 + 脚本 + 凭据"四项估算，不要只算配置文件；
- 能力边界够用就不换；旧项目留在原地跑完，不一次性搬历史；
- 只有"上游不可能提供"才自研，且以增量移植为主；
- 规则、记忆、验收脚本放在框架之外，让下一次迁移的重建成本接近零。
