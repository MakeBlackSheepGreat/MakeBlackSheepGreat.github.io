# 把核验做到渲染级：断言、截图与字节比对

> 2026 年 9 到 10 月维护双语站点时定下来的做法。那一轮改了十几个页面，文件属性检查全部通过，但我仍然不敢说"改对了"——因为同样的检查在更早一轮里漏掉过渲染问题。这篇讲后来固化的三层核验。

::: info 先说结论
- 文件属性检查只能证明"文件对了"，证明不了"页面对了"：关键词在 HTML 源码里，不等于它渲染出来了；
- 核验分三层：**构建产物取文 → 渲染级断言 → 线上字节比对**。上一层过不了，下一层没有意义；
- **流水线成功不等于部署生效**。终验要抓线上真实页面，判据是线上字节数等于本地产物字节数；
- 断言要写"不该出现的也消失了"，只写"包含"会漏掉"该删的没删"这一类最贵的错误。
:::

## 一、为什么文件属性不够

静态站点的正文常由前端脚本注入。用命令行工具直接抓页面，拿到的往往只是一个几百字节的外壳，正文一个字都不在里面。这时候去数关键词，数的是模板而不是内容。

还有一类更隐蔽的：源码里确实有这个词，但选择器写错了，浏览器里根本没渲染出对应元素。文件检查对这一类完全失明。

踩过的一个具体例子：自定义容器在源码里写 `card`，渲染出来的 CSS 类名却是 `entry`。按容器名去等 `.card`，等待一直超时；按渲染结果去等 `.entry`，立刻就绪。**核验的选择器必须从渲染结果反推，不能从源码写法推断。**

## 二、三层核验

| 层级 | 手段 | 能发现什么 | 不能发现什么 |
| --- | --- | --- | --- |
| 构建产物 | 从产物文件里取真实文本 | 内容没进产物、文案被截断 | 渲染问题、线上问题 |
| 渲染级断言 | 无头浏览器打开页面，对可见文本断言 | 元素没渲染、旧文案没删干净、布局溢出、脚本报错 | 业务逻辑是否正确 |
| 线上字节比对 | 抓线上页面与本地产物比字节数 | 没部署、部署了旧版本、CDN 缓存不一致 | 内容质量 |

第一层最便宜，先跑；第三层最接近用户所见，最后跑。顺序反了会浪费：渲染级断言跑在没更新的产物上，通过与否都没有意义。

## 三、断言怎么写才不漏

一组可用的断言至少覆盖五个方向，缺一个就有一类漏网：

| 方向 | 写法 | 拦住什么 |
| --- | --- | --- |
| 必须出现 | 新文案的关键词逐条断言 | 改动没生效 |
| 必须消失 | 旧措辞逐条断言不在页面里 | 该删的没删、新旧混排 |
| 分区归属 | 只截取某个标题下的文本再断言 | 内容跑错了区块 |
| 结构完整 | 卡片数量、列表项数 | 少渲染了一条 |
| 运行时健康 | 横向溢出、页面级脚本错误 | 样式破了、交互瘫了 |

两点经验。**断言必须可数**：跑完给出"通过 88，失败 0"，而不是一句"检查通过"。不可数的结论无法对账，也无法在下一轮复用。**分区断言比全文断言更重要**：同一句话可能同时出现在"已获奖"和"未获奖"两个区，全文能搜到不代表它归对了位置。

另外，每轮核验都存一份全页截图。截图是给人在改下一轮之前看的，也是给验收留的证据。

## 四、部署核验：流水线成功不是终点

两条发布流水线都显示成功之后，仍然要自己抓一遍线上页面。见过流水线全绿而页面还是旧版的情况，原因包括缓存、构建目录串用、分支配置错位。

判据定得很硬：**线上字节数等于本地产物对应页面的字节数**。字节数一致，基本可以判定部署无偏差；不一致，再逐项查。

命令行抓取有两个坑。一是不指定编码时拿到的压缩响应会让下载量统计报 0，要显式要求不压缩。二是批量连续请求可能出现连接失败，表现和"站点挂了"完全一样；逐个重试后往往全部正常。**看到一批失败先重试，再下结论。**

## 五、可复用的清单

- 核验分三层：产物取文、渲染断言、线上字节比对，按顺序跑；
- 断言覆盖必须出现、必须消失、分区归属、结构数量、运行时健康五个方向；
- 断言结果必须给出可数的通过与失败条数；
- 选择器从渲染结果反推，不从源码写法推断；
- 每轮留全页截图，作为改下一轮之前的依据；
- 流水线成功后仍抓线上页面，按字节数判定是否生效；
- 抓线上页面要求不压缩响应，失败逐个重试再判断。
